Alerts

Alerts.

List the alerts you send. Each MSP chooses where they land in their stack. Bitlync routes them. You do not pick a board, a team, or a form for them.

There is no breaking change to POST /tenants/{tenant_id}/alerts. The Activity tab does not add an API. Billing and Alerts write routes share one abuse limit. HTTP 429 is unchanged. See Rate limits.

Setup

Turn on Send alerts to MSP tickets in Configure > Features. Setup offers Scan your website, Upload a list (CSV or Excel), or Add by hand, then a review before the list is live.

Add by hand, and any later edit, is PUT /isv/alert-types (the same body as PUT /tenants/{tenant_id}/alert-types). That call replaces the whole catalog. It does not merge. A type you leave out is removed. Category is required. Severity is Critical, High, Medium, Low, or Info. The row menu can edit, rename, or remove a type. Removing the last type returns to this guided setup.

Upload a list on the API is POST /isv/alert-types/import. The body is {"csv": "..."}. Columns are name, description, type, and severity. Nothing is saved. Rows come back as drafts for review. A CSV with no name column returns 422 request_invalid and the message "The CSV needs a name column." On a trial row, the type column came back as a tag and the category was Product alerts. The OpenAPI file on this site is still 0.94.0 and does not list this route. The sandbox serves OpenAPI 0.99.0.

The upload limit is 2 MB for Alerts and for a Billing price list. An alert import body over 2 MB returned 413 request_invalid and the message "Reload the page and try again." The upload screen also uses "That file is too large. Use a CSV or Excel file under 2 MB." The sandbox API did not return that sentence.

Scan your website is not available on the sandbox. POST /isv/alert-types/fill returned 404 unknown_resource and the message "Not found." The sandbox description says the reader is not in this build. Treat fill-from-site as deploy pending, not live.

MSP connect

Connect adds an alerts setup step with Back and Continue. The MSP chooses where alerts go, using fields from their stack. Type is required. Subtype (ConnectWise), Item, and the Halo subcategory are optional and default to None. The error "ConnectWise requires Subtype on {board}." is returned only when the stack mandates Subtype. The sandbox stack options for the fixture ConnectWise tenant list Board, Type, Subtype, and Item. One Item name in that fixture is None. The sandbox did not return the Subtype error string. No board was saved on that call.

If the save cannot be read back, the message is "Reload the page and try again." If saves come too fast, the message is "Too many saves. Wait a minute and try again." The oversized import above is the call that returned the reload sentence. The sandbox did not return "Too many saves. Wait a minute and try again."

The Done page links "Go to Activity". The sandbox Connect preview that was fetched was still on the keys step, so that link was not in the HTML. The step rail was Choose, Connect, Configure, Map companies, Done.

Activity

The portal Activity tab has Needs your attention, a change log in the viewer's local time, Deliveries, and Send test ticket. Send test ticket on that tab is sandbox-only, 30 per minute. The console Activity destination returned 401 for the sandbox demo key, so this tab was not opened.

POST /tenants/{tenant_id}/alerts/test with dry_run true on the sandbox returned a title [Bitlync test] CrowdStrike: no action required, safe to close. priority_name on that call was Informational. It did not create a ticket (dry_run true). Repeat alerts for the same device update one open ticket when dedupe is on. Bitlync does not reopen a ticket the MSP closed. That dedupe rule is already in the alert send description.

Where an alert goes

GET /tenants/{tenant_id}/alert-routing is on the sandbox (OpenAPI 0.99.0), not in the OpenAPI file on this site (0.94.0). For the sandbox ConnectWise tenant the rule was: Critical and High go to Ticket, Medium goes to Email, Low and Info go to Daily digest.

Deploy pending

Production deploy is still pending for the alerts v4 slice and for the later MSP send-to slice. Do not treat the following as live.

  • Fill from site. The sandbox route returns 404 "Not found."
  • No-default footers and the "where alerts go" empty state, beyond the routing rule above.
  • MSP Send to as a flat checkbox list.
  • One "Tickets go to" footer per section, with a Send test ticket link in that footer.
  • Autosave with a quiet check mark.
  • Subscriptions tickets stay Off until the MSP picks a destination.
  • The vendor alert-type menu adds Duplicate beside Rename, Edit, and Remove.
  • A test ticket the MSP closes from Bitlync. The sandbox lists POST /connect/{token}/alerts/test/close ("Close the test ticket this session created."). This pass did not create or close one.

The sandbox Connect preview footer already reads "Powered by bitlync". The pending slice says the footer shows only that line.
