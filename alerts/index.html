Alerts

Alerts.

List the alerts you send. Each MSP chooses where they land in their stack. Bitlync routes them. You do not pick a board, a team, or a form for them.

There is no breaking change to POST /tenants/{tenant_id}/alerts. The Activity tab does not add an API. Billing and Alerts write routes share one abuse limit. HTTP 429 is unchanged. See Rate limits.

Setup

Turn on Send alerts to MSP tickets in Configure > Features. Setup offers Upload a list (CSV or Excel) or Add by hand, then a review before the list is live.

Add by hand, and any later edit, is PUT /isv/alert-types (the same body as PUT /tenants/{tenant_id}/alert-types). That call replaces the whole catalog. It does not merge. A type you leave out is removed. Category is required. Severity is Critical, High, Medium, Low, or Info. The type menu is Rename, Edit, Remove, and Duplicate. Removing the last type returns to this guided setup.

Upload a list on the API is POST /isv/alert-types/import. The body is {"csv": "..."}. Columns are name, description, type, and severity. Nothing is saved. Rows come back as drafts for review. A CSV with no name column returns 422 request_invalid and the message "The CSV needs a name column." On a trial row, the type column came back as a tag and the category was Product alerts. OpenAPI 0.99.0 types that request as an object with no listed fields.

An Alerts or Billing upload is at most 2 MB. An alert write that is refused returns "Reload the page and try again."

Catalog

GET /isv/alert-types and GET /tenants/{tenant_id}/alert-types return the same rows. Omit limit and the whole catalog comes back, at most 200 types. limit is 1 to 200. Pass next_cursor back as cursor. next_cursor is null on the last page. count and total are the catalog size. A limit of 1 still returned count 11 and total 11, with one row in alert_types.

OpenAPI 0.99.0 types each 200 body as an object with no listed fields. The sandbox GET returned alert_types (array), count (number), total (number), next_cursor (string or null), and sandbox (boolean). On this key the ISV call had sandbox false and the tenant call had sandbox true.

Each row is id (string), name (string), description (string), category (string), group (string), group_label (string), tags (array of strings), notify_days (number or null), fix_line (string), draft (boolean), suggested_severity (string), and suggested_severity_label (string). Sync failing comes back with suggested_severity by_cause. The PUT severity check is the five names below, and by_cause is not one of them.

PUT /isv/alert-types and PUT /tenants/{tenant_id}/alert-types take the same body. OpenAPI 0.99.0 types it as an object with no listed fields. The operation description is {"alert_types": [{name, category, suggested_severity, description?, id?}]}. Category is required. A value that is not a list returns 422 request_invalid and "alert_types must be a list." Severity is Critical, High, Medium, Low, or Info. Anything else returns 422 request_invalid and "Severity must be Critical, High, Medium, Low or Info." At most 200 types. The body is at most 512 KB. A missing length is 411. An oversized body is 413. The 200 response is an object with no listed fields.

MSP connect

Connect adds an alerts setup step with Back and Continue. The MSP chooses where alerts go, using fields from their stack. Type is required. Subtype (ConnectWise), Item, and the Halo subcategory are optional and default to None. The error "ConnectWise requires Subtype on {board}." is returned only when the stack mandates Subtype. The sandbox stack options for the fixture ConnectWise tenant list Board, Type, Subtype, and Item. One Item name in that fixture is None. The sandbox did not return the Subtype error string. No board was saved on that call.

If the save cannot be read back, the message is "Reload the page and try again." If saves come too fast, the message is "Too many saves. Wait a minute and try again."

The Done page links "Go to Activity". The sandbox Connect preview that was fetched was still on the keys step, so that link was not in the HTML. The step rail was Choose, Connect, Configure, Map companies, Done.

Activity

The portal Activity tab has Needs your attention, a change log in the viewer's local time, Deliveries, and Send test ticket. Send test ticket on that tab is sandbox-only, 30 per minute. The console Activity destination returned 401 for the sandbox demo key, so this tab was not opened.

A test ticket title looks like [Bitlync test] {vendor display name}: .... On a sandbox dry run, priority_name was Informational, and dry_run true did not create a ticket. Repeat alerts for the same device update one open ticket when dedupe is on. Bitlync does not reopen a ticket the MSP closed. That dedupe rule is already in the alert send description.

Where an alert goes

Alert routing is owned by the MSP in Connect. Vendors should not call PUT /tenants/{tenant_id}/alert-routing to override it.

GET /tenants/{tenant_id}/alert-routing takes optional query vendor_key. Omitted, the spec default is connectwise. OpenAPI 0.99.0 types the 200 body as an object with no listed fields. The sandbox ConnectWise tenant returned vendor_key (string), rule (object), priority_map (object), coming_soon (array), dedupe_line (string), alert_types (array), count (number), and sandbox (boolean).

rule maps critical and high to ["ticket"], medium to ["email"], and low and info to ["daily_digest"]. priority_map maps those severities to Critical, High, Normal, Low, and Low. coming_soon is teams (Teams or Slack) and webhook (Webhook).

Each routing row is id (string), name (string), group (string), severity (string), send_to (array of strings), send_label (string), custom (boolean), off_allowed (boolean), by_severity (boolean), note (string), and notify_days (number or null). Connection problem came back send_to ["ticket", "email"] with off_allowed false. Sync failing came back severity by_cause, send_to [], and by_severity true.

GET /tenants/{tenant_id}/alert-routing
{
  "vendor_key": "connectwise",
  "rule": {
    "critical": ["ticket"],
    "high": ["ticket"],
    "medium": ["email"],
    "low": ["daily_digest"],
    "info": ["daily_digest"]
  },
  "coming_soon": [
    {"id": "teams", "label": "Teams or Slack"},
    {"id": "webhook", "label": "Webhook"}
  ],
  "count": 11,
  "sandbox": true
}

The PUT description names {"vendor_key", "send_to": {id: ["ticket", "email"]}, "reset": [id]}. Send to must always include Ticket or Email. OpenAPI 0.99.0 types that body as an object with no listed fields. The GET rule uses daily_digest for Low and Info.

Send

POST /tenants/{tenant_id}/alerts sends one alert. OpenAPI 0.99.0 types the body as an object with no listed fields. The operation description names type (name or id), severity (optional; the type's suggested severity when omitted), device (an object {id, name} or a string), customer, description (optional), dry_run (boolean, default false), and event_id or idempotency_key. The id is unique per event. A repeat needs a new id. The body is at most 64 KB. A missing length is 411. An oversized body is 413.

A call with a type and neither a customer nor a device returned 422 request_invalid and "Send a type, a customer, and a device." type subscription-renewal and type "Subscription renewal" both resolved. A string device was accepted. Omitting severity used the type's suggested severity, low for that row. Alerts off returns 409 feature_off before a vendor call.

POST /tenants/{tenant_id}/alerts
{
  "type": "subscription-renewal",
  "severity": "low",
  "device": {"id": "dev-1", "name": "FRONT-DESK"},
  "customer": "Acme Dental",
  "event_id": "docs-probe-dry-2026-10-21",
  "dry_run": true
}

OpenAPI 0.99.0 types the 200 body as an object with no listed fields. The sandbox dry_run true call returned success (boolean), source (string), source_id (string), ticket_ref (string), idempotent_replay (boolean), dry_run (boolean), sandbox (boolean), action (string), reason (string), reopen (boolean), dedupe (boolean), title (string), severity (string), priority_id (string), priority_name (string), message (string), destination (object), alert_type (the catalog row), and raw (object, the connector payload). On that call action was create, reason was new, reopen was false, dedupe was true, destination was {}, and priority_name was an empty string. The title was [CrowdStrike] Low · Subscriptions & billing · Subscription renewal · Acme Dental.

Test

POST /tenants/{tenant_id}/alerts/test sends a test through the same routing. The body is optional. OpenAPI 0.99.0 types it as an object or null, with no listed fields. {} returned dry_run true. The body is at most 64 KB. A missing length is 411. An oversized body is 413.

The 200 body has the same fields as send. On the sandbox, title was [Bitlync test] CrowdStrike: no action required, safe to close, severity was critical, priority_name was Informational, priority_id was 8, and dry_run true did not create a ticket. alert_type was a sample row: id test-alert, name Test alert, category Security events, group product, suggested_severity critical. The catalog already had 11 types on that call.

Snooze

GET /tenants/{tenant_id}/alert-snoozes lists snoozes for this MSP. At most 500 are stored. limit is 1 to 100. Omitted, the page size is 25. Pass cursor for the next page. OpenAPI 0.99.0 types the 200 body as an object with no listed fields. The sandbox returned snoozes (array), count (number), next_cursor (string or null), and sandbox (boolean). An empty list is count 0 and snoozes [].

Each snooze is id (string), tenant_id (string), isv_key (string), scope (string), target_ref (string), target_label (string), alert_type_id (string), duration (string), ends_at (string or null), and created_at (string).

POST /tenants/{tenant_id}/alert-snoozes adds one. OpenAPI 0.99.0 types the body as an object with no listed fields. The description names scope (customer or device), target, duration (24h, 7d, or until_resolved), and alert_type_id (omit it for every alert). The body is at most 64 KB. Scope anything else returns 422 request_invalid and "Scope must be Customer or Device." Duration anything else returns 422 request_invalid and "Duration must be 24h, 7d, or Until resolved." The label "Until resolved" is stored as until_resolved. until_resolved comes back with ends_at null. 24h and 7d come back with an ends_at timestamp. An omitted alert_type_id is stored as an empty string.

POST /tenants/{tenant_id}/alert-snoozes
{
  "scope": "customer",
  "target": "docs-probe-cust",
  "duration": "24h"
}
200
{
  "snooze": {
    "id": "snz_8fdc48b1a10b70c9",
    "tenant_id": "sandbox-mainstreet",
    "isv_key": "demo-isv",
    "scope": "customer",
    "target_ref": "docs-probe-cust",
    "target_label": "docs-probe-cust",
    "alert_type_id": "",
    "duration": "24h",
    "ends_at": "2026-10-22T21:52:13.706524+00:00",
    "created_at": "2026-10-21T21:52:13.706524+00:00"
  },
  "sandbox": true
}

POST /tenants/{tenant_id}/alert-snoozes/{snooze_id}/undo removes that snooze. The 200 body on the sandbox was {"removed": "snz_8fdc48b1a10b70c9", "sandbox": true}. removed is the id string. The route description says a snooze on another MSP is 404. OpenAPI 0.99.0 types that 200 body as an object with no listed fields.

Send to

MSP Send to is a flat checkbox list. Each section has one "Tickets go to" footer, with a Send test ticket link. The choice autosaves, and a quiet check mark shows when it has saved. Subscriptions tickets stay Off until the MSP picks a destination. The MSP can close the test ticket from Bitlync.

The footer is "Powered by bitlync", with a lowercase b.
